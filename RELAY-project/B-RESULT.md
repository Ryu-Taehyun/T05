# 세션 B 검증 결과

2026-10-22. B는 HANDOFF.md의 일곱 항목과 outputs의 저장된 소스·JSON만 읽고 작업했다. A의 이전 대화는 참조하지 않았다.

## 변경

- index.html의 비어 있던 파일 불러오기 이벤트를 완성했다.
- 2 × 1024 × 1024 바이트 초과 파일을 읽기 전에 거절하고, JSON/스키마 검증을 마친 후 교체를 확인한다.
- 취소·잘못된 파일·읽기 오류 시 보드와 저장값을 유지한다. 성공하면 작업, 세 가지 메모, 검색, 진행률을 동기화하고 저장한다. 검색은 빈 값으로 초기화한다.
- 기존 저장소 읽기 실패로 storageReady=false이면 파일을 불러와도 저장을 재개하지 않는다. 저장 용량 오류 안내도 성공 안내에 덮이지 않는다.
- 파일 선택값을 비워 같은 파일을 재선택할 수 있다. 늦게 끝난 이전 파일 읽기가 새 선택 결과를 덮어쓰지 않도록 시도 번호를 비교한다.

## 실행 증거

Windows, Node v24.19.0에서 다음을 실행했고 종료 코드 0이었다.

```text
node outputs/verify-b.cjs
T01 PASS
T02 PASS
T03 PASS
T04 PASS
T05 PASS
T06 PASS
T07 PASS
T08 PASS
T09 PASS
T10 PASS
```

verify.cjs는 수정하지 않았다. B의 verify-b.cjs는 그 파일의 run()을 호출해 고정 T01~T08 기준을 그대로 실행한다.

T09: 저장소가 비어 있는 새로운 UI 실행 컨텍스트에 A-handoff.json을 실제 onchange 핸들러로 넣었다. 네 작업과 세 메모, 25% 완료율이 일치했다. 저장된 내용을 또 다른 새 UI 컨텍스트에서 복원해 전체 상태 일치를 확인했다. 이후 고정 T01~T08을 각각 새 모델 컨텍스트에서 재실행했다. 가져온 네 작업을 T01의 세 샘플과 혼동하지 않았다. 공통 상황의 ‘회의 자료 정리’를 진행 중으로 변경하고 다음 메모를 ‘발표 리허설’로 수정한 뒤 실제 내보내기 핸들러가 만든 Blob을 다른 새 UI 컨텍스트의 불러오기 핸들러에 넣어 전체 상태 일치를 검증했다.

T10: 성공, 교체 확인 취소, 잘못된 JSON, 중복 ID, 잘못된 상태, 2MB 초과, 파일 읽기 실패를 검증했다. 실패·취소에서는 기존 보드가 같고 저장 호출은 0회임을 확인했다. 정확히 2MB는 허용했고, 선택 파일 없음은 무변경이었다. 저장소 읽기 실패 후 원본 저장값 유지와 쓰기 0회, 저장 실패 안내 유지, 이전 비동기 읽기 결과 무시도 검증했다.

## 검증 범위와 한계

모델 및 UI 이벤트 함수는 독립 Node VM에서 실행했다. DOM, File.text(), localStorage, confirm, 다운로드 URL은 검증용 대역을 사용했다. 실제 브라우저 클릭, 운영체제 파일 선택창, 실제 파일 다운로드, 브라우저 저장소 정책, 화면 배치·접근성·모바일 화면은 검사하지 않았다. 새 환경 재현은 새 VM 전역과 새 저장소를 뜻하며, 별도 실제 브라우저나 별도 컴퓨터 검증은 아니다. 이 한계를 통과로 표현해서는 안 된다.

B가 수정한 파일: index.html, verify-b.cjs, B-RESULT.md. A-handoff.json과 verify.cjs는 보존했다.
